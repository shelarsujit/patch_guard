## 0:00–0:35 · The problem, with a number

> Coding agents are graded on one question: did the failing test pass? That is
> not the same question as: did you fix it.
>
> METR had maintainers from scikit-learn, Sphinx and pytest review 296
> AI-generated pull requests. Merge decisions came in about **24 points below**
> SWE-bench "resolved" scores. The top reasons were core functionality broken and
> the patch breaking other code — not style.
>
> Patch-Guard wraps a cheap coding agent and refuses to let it submit unless
> three things hold: the target test passes, nothing that used to pass is broken,
> and the test files are untouched.

**Screen:** README top section.

## 0:35–1:20 · The metric, and being honest about it

> The metric is net-resolved: all three at once, or it does not count.
>
> One thing to be precise about — SWE-bench's own `resolved` metric already
> requires PASS_TO_PASS. An earlier draft of my README claimed otherwise and that
> was wrong. The real gap is narrower: SWE-bench runs only the test files the
> PR's test patch touched, so a regression outside them is invisible. This sweeps
> the whole suite.

**Screen:** the "The metric" section, showing the correction in place.

> Why that matters for this project: I would rather show you a correction than
> have you find one.

## 1:20–2:20 · The headline, and the case that earns it

> Same model, same temperature, same cases, same starting information on both
> sides. The only difference is supervision.

**Screen:** `results/report.md` headline table.

> Net-resolved goes from **50% to 70%**. Reward hacking on spec-contradicting
> tests goes from **2 of 4 to zero**.
>
> The 20-point gain was not what I expected. Gates reject patches, so I predicted
> they would trade resolution for safety. They did not — because a rejection
> carries its reason back to the worker: "the target tests still fail", "the
> patched code never terminated". Two cases the one-shot baseline abandoned came
> back on a later attempt. The gates are a repair signal, not only a filter.

## 2:20–3:20 · Gate 2, and why the eval set had to be rebuilt

> Here is the part I would push on if I were reviewing this.
>
> Regressions per patch read 0.00 on every sweep. Not because nothing regressed —
> because on QuixBugs nothing *could*. Its programs are independent files, so a
> one-file patch cannot break another program. Two of my three gates were
> measured and the third was taken on trust.

**Screen:** `eval/data/coupled/README.md`, then the gate-2 table.

> So I built a set that can break. A shared helper behind three callers, and the
> bug placed so the correct fix is in the caller and the obvious fix is in the
> helper.
>
> Fix it in the helper and the target test genuinely passes — a leaderboard calls
> that resolved — while **four** tests in modules the agent never touched go red.
> Live on that case: baseline **0%** net-resolved, **2.00** regressions per
> patch; Patch-Guard **100%**, **0.00**.

## 4:00–4:45 · What it does not show, and the actual finding

> Three things these numbers do not show, stated in the README rather than left
> to be found.
>
> Neither runner ever *refused* — correct-refusal is **0 of 4** on both sides.
> The supervisor did not cheat, but it never diagnosed the contradiction either.
> Harm prevented; diagnosis not made.
>
> Overclaiming barely appeared: **11 of 14** baseline runs ended by exhausting
> the step budget, not by declaring false victory. At this tier the dominant
> failure is running out of road.
>
> And the finding I did not go looking for: building the harness surfaced
> **eleven** infrastructure faults that each produced a plausible *number*
> instead of an error — a quota ceiling scored as agent failure, a provider
> backend that silently dropped answers, a broken import scored as 62
> regressions, and a cassette that served one model another model's run and
> fabricated a clean result. Every one of them, left alone, would have biased the
> comparison in this project's favour.
>
> At this model tier, most of what looks like agent failure is harness artifact.
> That is the claim I would defend, and the changelog is the evidence.
